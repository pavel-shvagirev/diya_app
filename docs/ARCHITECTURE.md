# Архитектура

Приложение на Electron, код в трёх процессах:

| Слой     | Где            | Роль                                                                                                                             |
| -------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Main     | `src/main`     | API Яндекс Диска, синхронизация, токены, окна, трей, меню. Node.js.                                                              |
| Preload  | `src/preload`  | Типизированный `window.api` (`contextBridge`); собирается esbuild в CommonJS, потому что preload в песочнице не умеет ES-модули. |
| Renderer | `src/renderer` | Интерфейс на React + Zustand. Песочница, без доступа к Node.                                                                     |
| Shared   | `src/shared`   | Имена IPC-каналов, типы, проверка путей и URL, переключатели функций.                                                            |

## Главный процесс

- **`main.ts`** — запуск и жизненный цикл: создаёт сервисы ниже, связывает IPC, трей и меню,
  блокировка единственного экземпляра, выход. В покрытие юнит-тестами не входит; его проверяет
  e2e-прогон.
- **`yandex-api.ts`** — REST-клиент `https://cloud-api.yandex.net/v1/disk` (листинг с
  пагинацией, плоский список всех файлов, ссылки загрузки/скачивания, copy/move/delete/mkdir,
  publish/unpublish, корзина с её папками и восстановлением под новым именем, операции). Повторы
  при 429/5xx с задержкой, опрос 202-операций (только на адресе API), при 401 один раз пробует
  refresh-токен, иначе выход. Вызовы принимают необязательный `AbortSignal`.
- **`network.ts`** — направляет все `fetch` главного процесса через undici 8 (HTTP/1.1): клиент из
  Electron 45 может обрушить процесс, пока скачиваемый файл ещё записывается (nodejs/undici#5360).
  Вызывается первым в `main.ts`.
- **`oauth.ts`, `auth-service.ts`, `app-config.ts`, `token-store.ts`** — вход по _device flow_
  Яндекс OAuth (код показывается в программе, подтверждается в браузере; без redirect URI; ID и
  секрет собственного приложения пользователя), обновление токена, выбор Client ID (введённый → `YADISK_CLIENT_ID`;
  в сборках ID нет), зашифрованный файл сессии.
- **`language.ts`** — язык интерфейса (система / ru / en, хранится в `settings.json`): нативные меню
  читают его напрямую, страницы получают `?lang=` при загрузке, поэтому смена перезагружает окна.
  Строки: `src/renderer/lib/strings.ts` (страницы) и `menu-strings.ts` (меню, трей).
- **`transfer.ts`** — потоковая загрузка/скачивание с прогрессом по байтам; скачивание идёт в
  `*.part` и переименовывается при успехе.
- **`sync-engine.ts`, `sync-db.ts`, `fs-watcher.ts`, `remote-storage.ts`, `sync-control.ts`** —
  см. ниже.
- **`ipc-handlers.ts`** — все вызовы `window.api`; проверяет пути и аргументы («показать в папке» —
  только для папки синхронизации и папки данных приложения).
- **`logger.ts`, `log-window.ts`** — кольцевой буфер + файл с ротацией, скрытие секретов, окно журнала.
- **Окна и меню:** `window-holder.ts` (пересоздаёт главное окно по требованию),
  `quit-guard.ts` + `hint-window.ts` (двойное Cmd/Ctrl+Q), `tray.ts`, `app-menu.ts`,
  `quit-key.ts` (защищённое Cmd/Ctrl+Q внутри окон), `app-icon.ts` (иконка окна и Dock),
  `menu-strings.ts`, `security.ts` (защита навигации, CSP, обёртка `safeStorage`).

## Синхронизация

Одна пара (локальная папка ⇄ папка на Диске). Каждый запуск (таймер 60 с, события файлов,
«синхронизировать сейчас»):

1. Сканируются оба дерева, читается последнее согласованное состояние из `sync_state` (SQLite).
   Диск читается папка за папкой или, если синхронизируется весь Диск, в основном плоским
   списком файлов (см. ниже).
2. Для каждого пути по _(локально, на Диске, последнее состояние)_ выбирается: загрузка,
   скачивание, конфликт, удаление с одной стороны или ничего; причина пишется в журнал (debug).
3. Выполнение: сначала папки, потом файлы, удаления в конце. После загрузки сверяется размер на
   Диске; повреждённая копия удаляется и сообщается как ошибка.

Между запусками проходит не меньше 5 с («синхронизировать сейчас» не ждёт и стартует сразу), а тик таймера во время запуска ничего не ставит в
очередь. Файл, на который Диск отвечает 5xx или 429, не запрашивается снова 1 мин, затем 2, 4 …
до 30 мин (всё это время он числится в ошибках).
Пауза (`stop()`) отменяет идущий запуск: все запросы и передачи запуска несут один
`AbortSignal` (`RemoteStorage` принимает его последним аргументом), поэтому листинг или передача
обрываются сразу, недокачанный `*.part` удаляется, а запуск заканчивается как «на паузе»: не
записывается как завершённый и ошибкой не считается. Пауза во время зазора в 5 с отменяет ждущий
запуск, выход из приложения тоже ставит на паузу. Клик «синхронизировать сейчас» во время запуска
повтор не ставит.

**Чтение Диска.** У API нет ленты изменений, а листинг папки стоит запрос на папку. Если корень
синхронизации `/` (весь Диск) и удалённая сторона умеет (`RemoteStorage.listAllFiles`,
`GET /v1/disk/resources/files`), папки обходятся только на первом запуске, по «синхронизировать
сейчас», через 30 минут (`fullScanMs`) и после того, как Диск отказал в плоском списке (HTTP 400,
помнится до конца сеанса); остальные запуски читают плоский список: запрос на 1000 файлов и только
нужные поля (`fields`). В плоском списке папок нет: они берутся из путей файлов, а пустые помнятся
с последнего полного обхода, но лишь как догадка: плоский запуск ничего не создаёт и не удаляет
из-за неё (пустая папка, созданная или удалённая на Диске в промежутке, разбирается при следующем
полном обходе). Изменения через файловый менеджер (удаление, копирование, перенос, новая папка,
загрузка, восстановление из корзины) вызывают `SyncEngine.invalidateRemote()`, и следующий запуск
читает дерево целиком. Список читается постранично, пока Диск меняется, поэтому файл может проскочить: файл,
который лишь _отсутствует_ в плоском списке, удаляется локально только после того, как `stat`
ответит 404. Любой другой сбой плоского списка завершает запуск. Папка синхронизации, отличная от
`/`, всегда обходится по папкам.

**Папки.** Папка, виденная с обеих сторон на запуске, записывается в `sync_state`. Записанная
папка, пропавшая с одной стороны, удалена там, и удаление переносится на другую сторону (в
корзину Диска или системную корзину), самые вложенные последними, но только если внутри не
осталось ничего, что не было удалено вместе с ней. Если на другой стороне есть не удалённый файл
(добавленный в промежутке, изменённый или скрытый), папка создаётся заново на той стороне, где её
не стало, и решает содержимое; локальная папка, где остались скрытые файлы пользователя,
сохраняется. Папка, ни разу не виденная с обеих сторон, новая и создаётся на другой стороне.
Удаление папок решается только после полного обхода, никогда по отсутствию папки в плоском списке.

Правила безопасности: файл, изменённый с обеих сторон, сохраняется в двух версиях; файл, который
пока нельзя сравнить по размеру/md5, ждёт следующего запуска; файлы, изменённые менее 2 с назад,
откладываются; запуск, где удалений больше 50 % известных файлов (и не меньше 10), отклоняется,
если список на Диске выглядит опустошённым или исчезла локальная папка; локальные удаления
переносятся в корзину Диска.

## Надёжность слоя API

- У каждого запроса к API есть таймаут (30 с, включая тело). После сетевого сбоя повторяются
  только чтения (GET): потерянный ответ на запись может скрывать состоявшуюся запись. 429 и 5xx
  повторяются с паузой, `Retry-After` сервера (секунды или дата, не дольше минуты) главнее.
- Ошибки — `YandexApiError` (`api-error.ts`): `status`, `error`-код API и `description`. Код
  ветвится по `errorStatus()`, а не по тексту сообщения.
- 202 опрашивается только если ссылка — это статус операции на хосте API
  (`/v1/disk/operations?id=…` или `/operations/<id>`).
- Передачи (`transfer.ts`): предел на соединение, на молчание при идущих байтах и на ответ Диска
  после загрузки; загрузка повторяется после 500/503 или сбоя соединения с новой ссылкой;
  скачанное проверяется (размер, md5, объявленная длина) до того, как заменит что-либо.
  Каждый вызов принимает `AbortSignal` (пауза, выход): после него ничего не отправляется, а
  идущая загрузка или скачивание обрывается и не повторяется.
- Перед загрузкой от 64 МБ (не перезапись: размер старой копии неизвестен) читается свободное
  место (`GET /v1/disk/`); если файл не помещается, сразу ошибка 507 с цифрами; если квоту
  прочитать нельзя, загрузка идёт дальше и решает Диск. 507 движок синхронизации не откладывает:
  следующий запуск пробует снова.

## Модель безопасности

Renderer в песочнице с изоляцией контекста; строгий CSP; проверка аргументов IPC; токен
доступа уходит только на хост API (`cloud-api.yandex.net`), секрет приложения и refresh-токен —
только на хост OAuth (`oauth.yandex.ru` / `.com`); внешние ссылки — только HTTPS и список доменов; сессия
шифруется хранилищем ключей ОС; функция с известной проблемой выключается в
`src/shared/features.ts` и отклоняется в главном процессе, а не только скрывается в интерфейсе.

Ещё: каждый IPC-обработчик проверяет, что сообщение пришло с нашей страницы
(`isTrustedSender`); все запросы разрешений отклоняются; папка синхронизации отклоняется, если это
весь диск, домашняя папка, системная папка или пересечение с данными приложения
(`sync-folder.ts`); символические ссылки не разворачиваются (загрузка, сканирование синхронизации); ссылки загрузки и
скачивания должны быть https; без настоящей связки ключей ОС (Linux `basic_text`) ничего не
сохраняется; в сборках отключены `runAsNode`, `NODE_OPTIONS`, `--inspect`, чтение вне asar, включена
проверка целостности asar.

## Тесты

`tests/contract` прогоняет клиент на примерах ответов из официального справочника
(`official-examples.ts` указывает страницу каждого); прежде чем опираться на новую форму ответа,
добавьте её пример туда.

`npm test` (Vitest, happy-dom). Модули главного процесса тестируются с внедрёнными зависимостями;
слой передачи дополнительно — на настоящем локальном HTTP-сервере; хранилища и компоненты
интерфейса — Testing Library. Формы ответов API в тестах взяты из официальной документации.

`npm run e2e` (`e2e/smoke.cjs`) запускает настоящее приложение против Диска в памяти
(`e2e/fake-disk.cjs`) с одноразовым профилем и проверяет вход, обзор, создание/удаление/
восстановление, синхронизацию и смену языка; нужен дисплей, в CI не входит.
